## Эксперимент с очередями выполнения

До запуска `npm run example:order` был записан прогноз порядка меток. После запуска получен фактический порядок и составлено объяснение.

| Этап                  | Порядок меток    | Объяснение                                                                                                                                         |
| --------------------- | ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| Прогноз до запуска    | A, B, C, D, E, F | Сначала синхронный код, затем микрозадачи (Promise, await), затем макрозадачи (таймер).                                                            |
| Фактический результат | A, B, C, D, E, F | `A`, `B` (начало async), `C` — синхронный код. `D` (обработчик Promise) и `E` (продолжение после await) — микрозадачи. `F` — макрозадача (таймер). |

**Дополнительные пояснения:**

- К синхронному коду относятся: `A`, `B` (до `await`), `C`.
- В очередь микрозадач попадают: `D` (колбэк `.then()`) и `E` (продолжение асинхронной функции после `await null`).
- Таймер с задержкой `0` (`F`) не выполняется немедленно, так как попадает в очередь макрозадач (task queue), которая обрабатывается только после того, как стек вызовов опустеет и завершатся все микрозадачи.
- Если удалить обработчик Promise, метка `D` пропадет, порядок будет `A, B, C, E, F`.

## Организация кода

| Файл                | Ответственность                                                                                                                                                   |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `api/server.mjs`    | Готовый локальный HTTP-сервер. Обрабатывает GET-запросы, фильтрует данные, отдает JSON и ошибки.                                                                  |
| `src/api-client.js` | Общий транспортный клиент. Умеет собирать URL (`buildUrl`), делать `fetch`, проверять заголовки, обрабатывать тайм-ауты/отмену и упаковывать ошибки в `ApiError`. |
| `src/task-api.js`   | Доменный слой. Знает маршруты (`/tasks`, `/categories`), проверяет входные фильтры и валидирует ответы сервера по схеме.                                          |
| `src/variant.js`    | Конфигурация индивидуального варианта (номер и фильтры).                                                                                                          |
| `src/main.js`       | Точка входа для консольного сценария: запускает клиент, выводит таблицу и перехватывает ошибки.                                                                   |

`fetchFn` передается в `createApiClient` аргументом для того, чтобы модуль можно было протестировать без реальной сети (подменив функцию). HTTP-ошибки проверяются отдельно от сетевых, потому что `fetch` не отклоняет Promise при статусах 4xx и 5xx (ответ получен, но он с ошибкой). JSON после разбора проверяется по контракту, потому что синтаксически корректный JSON (например, `{"data": "не массив"}`) может не соответствовать ожидаемой структуре приложения.

## Реализация общего клиента

| Требование                   | Как реализовано                                                | Проверка                                              |
| ---------------------------- | -------------------------------------------------------------- | ----------------------------------------------------- |
| Нормализация `baseUrl`       | Проверка через `new URL()`, запрет относительных путей и query | `createApiClient` бросает `TypeError` при ошибках.    |
| Кодирование query-параметров | Использование `URLSearchParams` и `Object.entries`             | Пробелы и кириллица корректно кодируются.             |
| Заголовок `Accept`           | Передается в `headers` при вызове `fetchFn`                    | `accept: application/json`.                           |
| Проверка `response.ok`       | Явное условие `if (!response.ok)`                              | Генерируется `ApiError` с `kind: "http"`.             |
| Проверка `Content-Type`      | Проверка наличия `application/json` в заголовке                | Генерируется `ApiError` с `kind: "invalid-response"`. |
| Разбор JSON                  | `await response.json()` внутри `try/catch`                     | Ошибки парсинга дают `invalid-response`.              |
| Ограничение времени          | `AbortSignal.timeout(timeoutMs)`                               | Генерируется `ApiError` с `kind: "timeout"`.          |
| Внешняя отмена               | `AbortSignal.any([signal, timeoutSignal])`                     | Генерируется `ApiError` с `kind: "aborted"`.          |

## Последовательная и параллельная загрузка

Сравнение сценариев с задержкой 150 мс на каждый запрос через `/debug/delay`:

| Сценарий                     | Запуск 1, мс | Запуск 2, мс | Запуск 3, мс | Наблюдение                          |
| ---------------------------- | -----------: | -----------: | -----------: | ----------------------------------- |
| Два последовательных `await` |         ~305 |         ~302 |         ~310 | Время суммируется (150 + 150).      |
| `Promise.all`                |         ~152 |         ~155 |         ~150 | Время равно самому долгому запросу. |

`Promise.all` позволяет запустить оба запроса параллельно. Время ожидания сокращается, так как запросы не блокируют друг друга, а выполняются одновременно.
